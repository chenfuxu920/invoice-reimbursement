# 可配置发票匹配规则与配置界面设计

> 日期：2026-06-23
> 状态：已批准（待实现）

## 1. 背景与目标

### 1.1 现状

当前发票解析的匹配规则由三种硬编码机制混合实现：

- **关键词**：区域分割（`text.contains("销售方")`）、发票分类（约 30 个关键词散落在 `classify_from_regions` / `classify_from_full_text`）、行程单列映射（`COL_KEYWORDS`）、发票类型检测
- **正则**：所有字段提取（金额/销售方/日期/发票号/商品名）硬编码在 `field_extractors.rs`
- **坐标**：销售方回退、行程单表格锚点解析

配对逻辑（`pair_invoices_with_itineraries`）按总额 ±0.01 公差匹配。

项目已有一套 `TemplateManager` 框架（`template_manager.rs`），支持从 JSON 文件加载模板、`regex` 和 `section_field` 两种策略、`reload_from_config_dir()` 运行时重载、`InvoiceParser::with_config_dir()` 注入入口——但从未被实际使用：所有调用都是空构造 `InvoiceParser::new()`，项目里也没有任何模板文件。前端则完全没有配置界面（路由只有 导入/匹配/导出 三个）。

### 1.2 目标

将**字段提取正则**和**发票分类关键词**做成灵活可配置的，并添加配置界面，让用户可以根据手里新的发票修改适配规则。

### 1.3 范围

- **可配**：字段提取正则（金额/销售方/日期/发票号/商品名）、发票分类关键词
- **不可配（保持硬编码）**：区域分割关键词、行程单列映射、发票类型检测关键词、坐标锚点逻辑
- **配置界面**：双模式（可视化标注 + 手写正则），标注生成的规则可手动修改
- **测试机制**：单张实时测试

### 1.4 非目标

- 不做批量测试
- 不做 AI 辅助正则生成
- 不改造行程单解析的坐标锚点逻辑为可配置

### 2.2 解析时数据流

1. PDF → OCR → 全文 + 坐标
2. 遍历已启用模板（用户优先 → 内置），按 `priority` 降序，用模板的 `keywords` 匹配全文
3. 命中模板 → 用该模板的 `fields[].strategies` 提取字段
4. 模板未命中 → 回退现有硬编码逻辑（`classify_from_full_text` + `field_extractors`）
5. 提取出的字段 + 模板指定的 `category` → 输出 Invoice

### 2.3 配置时数据流

1. 用户在 `/templates` 页面增删改模板 → `save_template` 命令 → 写入 `user_templates/`
2. 标注模式：上传 PDF → OCR → 用户拖选文本 → 按字段类型套骨架生成正则 → 可编辑
3. 测试：上传 PDF → 用当前编辑中的模板（未保存也行）跑一次解析 → 返回各字段结果

### 2.4 关键设计原则

- 现有 `TemplateManager` 已支持 JSON 模板加载和 `reload`，本设计**激活并扩展**它，而非另起炉灶
- 硬编码逻辑保留作为最终回退，保证现有发票不受影响
- 内置模板随软件发布（只读），用户模板在 `app_config_dir`（可读写），升级不冲突
- 模板命中时**完全用模板**，不混用硬编码；未命中才回退。避免两套规则交叉干扰


### 3.2 字段说明

| 字段 | 作用 | 来源 |
|------|------|------|
| `keywords` | 模板匹配条件，全文包含任一即命中 | 现有结构已有 |
| `priority` | 多模板命中时的优先级，数字大优先 | 新增 |
| `enabled` | 可禁用模板而不删除 | 新增 |
| `category` | 该模板的默认分类（模板未配 category_keywords 时用） | 新增 |
| `category_keywords` | 分类关键词映射，覆盖现有硬编码的 `classify_from_full_text` | 新增 |
| `fields[].strategies` | 字段提取正则，按顺序尝试，首个成功即用 | 现有结构已有 |

### 3.3 分类逻辑

- 模板命中且有 `category_keywords` → 用模板的分类词判断分类
- 模板命中但无 `category_keywords` → 用模板的 `category` 默认值
- 无模板命中 → 回退现有硬编码 `classify_from_full_text`

### 3.4 字段类型与标注骨架映射

| 字段 name | 标注时套用的骨架生成逻辑 |
|-----------|------------------------|
| `amount` | 识别 `¥/￥/元` + 数字+逗号+小数点 → 生成 `前缀\s*([\d,]+\.?\d*)` |
| `date` | 识别年月日分隔符 → 生成 `(\d{4}[年/-]\d{1,2}[月/-]\d{1,2}日?)` |
| `invoice_number` | 识别"发票号码"+连续数字 → 生成 `发票号码[：:]\s*(\d{8,20})` |
| `seller_name` | 识别"名称："+后续文字 → 生成 `名称[：:]\s*(.+?)(?:\s\|$)`（`\|` 为正则的"或"，非表格分隔符） |
| `item_name` | 识别星号包裹或"项目名称：" → 生成 `\*(.+?)\*` 或 `项目名称[：:]\s*(.+)` |

骨架生成时保留用户拖选的**前缀文本**作为正则锚点（如用户选了"价税合计：¥1,234.56"，生成 `价税合计[：:￥¥]*\s*([\d,]+\.?\d*)` 而非纯数字匹配），这样正则更精确。前缀部分做字符类泛化（`：` → `[：:]`，`¥/￥` → `[￥¥]`），让生成的正则更健壮。

**标注流程**：

1. 上传 PDF → 后端 OCR 返回纯文本
2. 选择要标注的字段类型（金额/销售方/日期/发票号/商品名）
3. 在 OCR 文本上拖选该字段对应的文本片段
4. 系统按第 3.4 节的骨架逻辑自动生成正则，显示在下方文本框

6. 点"确认此字段"→ 正则填入模板编辑器对应字段
7. 重复 2-6 标注其他字段，全部完成后切回手写模式或直接保存

### 5.2 TemplateManager 激活与扩展

现有 `TemplateManager` 已有 JSON 加载和 `reload_from_config_dir()`，需补三件事：

**① 双目录加载**：

```
内置模板: app_data_dir/builtin_templates/*.json   (随发布打包，只读)
用户模板: app_config_dir/user_templates/*.json    (可读写)
```

加载时合并两个目录，用户模板同 id 覆盖内置模板（支持"复制内置→修改"的场景）。`source` 字段标记来源，前端据此决定能否编辑/删除。

**② 分类关键词支持**：

现有 `InvoiceTemplate` 缺 `category` / `category_keywords` / `priority` / `enabled` 字段，需扩展结构体。解析时模板命中后，分类判断优先走 `category_keywords`，其次 `category` 默认值。

**③ 解析流程集成**（改造 `InvoiceParser`）：

```
现有流程:
  parse() → split_into_regions() → classify_from_full_text() → field_extractors

改造后:
  parse()
    → 先尝试 match_template(text)  // 遍历已启用模板，按 priority 排序
    → 命中:
        extract_fields_by_template(template, text)  // 用模板正则提取
        classify_by_template(template, text)        // 用模板分类词
        → 返回 Invoice
    → 未命中:
        回退现有硬编码流程 (split_into_regions + classify_from_full_text + field_extractors)
```

关键原则：模板命中时**完全用模板**，不混用硬编码；未命中才回退。避免两套规则交叉干扰。

### 5.3 标注骨架生成器

新增 `regex_skeleton.rs` 模块，纯函数，无副作用：

```rust
pub fn generate_regex(field_type: FieldType, selected_text: &str) -> String
```

| FieldType | 生成逻辑 |
|-----------|---------|
| Amount | 检测 `¥/￥/元` 前缀 → 保留前缀 + `[\d,]+\.?\d*` 捕获组 |
| Date | 检测 `年/月/日` 或 `-//` 分隔 → `(\d{4}[年/-]\d{1,2}[月/-]\d{1,2}日?)` |
| InvoiceNumber | 检测"发票号码"前缀 → 保留前缀 + `(\d{8,20})` |
| SellerName | 检测"名称："前缀 → 保留前缀 + `(.+?)(?:\s\|$)`（`\|` 为正则的"或"，非表格分隔符） |
| ItemName | 检测星号 → `\*(.+?)\*`；或"项目名称："前缀 |

前缀部分做字符类泛化（`：` → `[：:]`，`¥/￥` → `[￥¥]`），让生成的正则更健壮。

### 5.4 内置模板种子文件

随软件发布 3-5 个内置模板 JSON，从现有硬编码规则提取：

- 增值税普通发票（从 `field_extractors.rs` 的正则提取）
- 增值税专用发票
- 滴滴行程单
- 酒店发票
- 天府通行程单

这些模板的初始内容 = 现有硬编码逻辑的等价 JSON 表达，保证激活后现有发票解析行为不变。

## 6. 错误处理与边界情况

### 6.1 错误处理

| 场景 | 处理方式 |
|------|---------|
| 用户正则语法错误 | `save_template` 和 `test_template` 时用 `regex::Regex::new()` 预编译，失败返回具体错误信息（行/列/原因），前端标红显示 |
| 正则编译成功但无捕获组 | 警告"该正则没有捕获组，无法提取字段值"，阻止保存必填字段 |
| 模板 keywords 为空 | 阻止保存，提示"至少需要一个识别关键词" |
| 模板 id 重复 | 用户模板保存时若 id 与内置冲突，自动覆盖内置（用户优先）；与另一用户模板冲突则提示重命名 |
| OCR 返回空文本 | 标注模式提示"OCR 未识别到文本，请检查 PDF"；测试模式返回"OCR 无文本" |
| 用户模板 JSON 损坏 | 加载时跳过损坏文件，日志记录，不影响其他模板和内置模板 |
| 模板提取结果为空但字段 required | 解析时该发票标记为"解析失败"，前端在导入页显示警告 |

### 6.2 边界情况

- **模板都不命中**：回退硬编码流程，保证现有行为不变
- **多个模板同时命中**：按 `priority` 降序取第一个；priority 相同则按 id 字母序，保证确定性
- **用户禁用了所有模板**：等价于全部回退硬编码，不报错
- **内置模板升级**：软件更新时内置模板目录被覆盖，但用户复制的用户模板不受影响（存在 user_templates/）
- **并发保存**：Tauri 命令在主线程串行执行，无并发问题；文件写入用临时文件+rename 保证原子性

## 7. 测试策略

### 7.1 后端 Rust 测试

| 测试模块 | 覆盖内容 |
|---------|---------|
| `regex_skeleton` | 每种 FieldType 的骨架生成：金额前缀泛化、日期多格式、销售方前缀保留等 |
| `template_manager` | 双目录加载、用户覆盖内置、损坏文件跳过、reload 刷新 |
| `template_matching` | keywords 命中/未命中、priority 排序、enabled 禁用跳过 |
| `template_field_extraction` | 各字段正则提取成功/失败、多 strategy 顺序回退、required 字段缺失 |
| `template_classification` | category_keywords 命中、回退 category 默认值、无分类词回退硬编码 |
| `regression` | 用现有测试发票跑改造后的解析，确保结果与硬编码一致（关键回归保护） |

**回归保护是重点**：现有 `invoice_parser` 测试全部保留，新增"模板模式 vs 硬编码模式"对比测试——同一批发票两种模式跑出的结果应一致。

### 7.2 前端测试

- 模板列表的增删改查交互
- 标注模式拖选→生成正则→可编辑流程
- 实时测试结果展示

## 8. 实现顺序

```
Phase 1: 后端基础（可独立验证）
  ① 扩展 InvoiceTemplate 结构体 + 双目录加载
  ② 内置模板种子文件（从硬编码提取）
  ③ 解析流程集成（模板优先→硬编码回退）
  ④ 回归测试通过

Phase 2: 后端命令 + 骨架生成器
  ⑤ Tauri 命令（list/get/save/delete/toggle/test/ocr/reload）
  ⑥ regex_skeleton.rs 骨架生成器 + 测试

Phase 3: 前端界面
  ⑦ /templates 路由 + 模板列表页
  ⑧ 模板编辑器（手写模式）
  ⑨ 实时测试面板
  ⑩ 标注模式（OCR 拖选→生成→编辑）

Phase 4: 收尾
  ⑪ 导入/导出模板 JSON
  ⑫ 端到端测试
```

每个 Phase 结束都有可验证的交付物。Phase 1 完成后即使没有前端，后端也能通过测试验证模板机制正确性。
