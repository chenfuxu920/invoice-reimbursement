# 发票报销自动化系统 — 需求规格文档

> 版本：1.0 | 更新日期：2026-05-07

---

## 1. 项目概述

### 1.1 背景

个人出差报销流程繁琐：需要收集纸质/电子发票、整理支付记录、手动填写报销表单、粘贴发票-支付对照材料。本项目旨在将此流程自动化。

### 1.2 目标

构建一个**离线桌面应用**，实现：
1. 发票自动识别（OCR）与结构化
2. 支付账单自动导入
3. 发票与支付记录智能匹配
4. 报销表单 PDF 一键生成

### 1.3 目标用户

- 出差人员（个人使用）
- 需要按单位报销模板整理发票和支付凭证的场景

### 1.4 设计原则

- **离线优先**：所有处理在本地完成，无需联网
- **隐私安全**：数据不上传任何云端服务
- **操作简单**：拖拽导入 → 自动处理 → 一键导出

## 2. 功能需求

### 2.1 发票收集与 OCR 识别

#### 2.1.1 输入来源

| 来源 | 格式 | 优先级 |
|------|------|--------|
| 手机拍照 | JPG/PNG 图片 | P0 |
| 电子发票 | PDF 文件 | P0 |
| 发票链接/二维码 | URL | P1 |

#### 2.1.2 OCR 提取字段

| 字段 | 说明 | 必须 |
|------|------|------|
| `amount` | 发票金额（价税合计） | ✅ |
| `seller_name` | 销售方名称 | ✅ |
| `item_name` | 项目名称/商品明细 | ✅ |
| `date` | 开票日期 | ✅ |
| `invoice_number` | 发票号码（用于去重） | ✅ |

#### 2.1.3 智能分类

系统根据 `seller_name` + `item_name` 自动分类：

| 类别 | 枚举值 | 识别关键词 |
|------|--------|------------|
| 高铁/车船票 | `Train` | 铁路、高铁、火车、客运站 |
| 飞机票 | `Flight` | 航空、机票、机场、航班 |
| 退改签/保险费 | `TicketChange` | 退票、改签、保险 |
| 市内交通 | `CityTransport` | 出租、网约车、滴滴、高德、t3、曹操 |
| 住宿费 | `Hotel` | 酒店、宾馆、住宿、招待所、民宿 |
| 餐饮费 | `Meal` | 餐饮、饭店、食品、餐厅、饭馆 |
| 其他 | `Other` | 以上均不匹配 |

#### 2.1.4 支持的发票类型

基于 `data/` 目录下的真实测试数据，支持以下场景：

| 发票类型 | 示例文件 | 说明 |
|----------|----------|------|
| 增值税电子发票 | `dzfp_*.pdf` | 含发票代码/号码/金额等标准字段 |
| 滴滴电子发票 | `滴滴电子发票*.pdf` | 网约车发票 |
| 滴滴行程报销单 | `滴滴出行行程报销单*.pdf` | 含多行程明细 |
| 天府通电子行程单 | `天府通电子行程单.pdf` | 公交/地铁行程 |
| 机票报销凭证 | `【飞猪】*.pdf` | 飞机票 + 退票手续费 |
| 酒店结账单 | `成都九眼桥美居酒店*.pdf` | 住宿明细 |

#### 2.1.5 OCR 技术要求

- **引擎**：PaddleOCR v5（嵌入式 ONNX 推理，paddle-ocr-rs 0.6.1）
- **模型文件**：
  - 检测模型：`ch_PP-OCRv5_mobile_det.onnx`（4.7MB）
  - 识别模型：`ch_PP-OCRv5_rec_mobile_infer.onnx`（16MB）
  - 分类模型：`ch_ppocr_mobile_v2.0_cls_infer.onnx`（572KB）
  - 字典文件：`ppocr_keys_v1.txt`（6622 字符）
- **单张识别时间**：< 3 秒
- **PDF 处理**：先转图片（pdftoppm），再逐页 OCR

### 2.3 发票-支付匹配引擎

#### 2.3.1 匹配模式

| 模式 | 场景 | 逻辑 |
|------|------|------|
| **一对一 (OneToOne)** | 高铁票、机票、住宿 | 1张发票 ↔ 1笔支付，金额匹配 |
| **一对多 (OneToMany)** | 打车（行程单+发票） | 1张发票 ↔ N笔支付，行程金额汇总匹配发票 |
| **手动确认 (ManualConfirmed)** | 自动匹配失败 | 用户手动选择配对 |

#### 2.3.2 匹配算法

```
对每张未匹配发票:
  1. 遍历未匹配支付记录
  2. 计算 |发票金额 - 支付金额|
  3. 若差值 ≤ tolerance（默认 ±1.00 元）→ 匹配成功
  4. 若为 CityTransport 类型 → 尝试一对多匹配（行程汇总）
  5. 无匹配 → 标记为 Unmatched，等待手动处理
```

#### 2.3.3 误差容忍

- 默认阈值：±1.00 元（可配置）
- 适配场景：优惠券、满减、四舍五入

#### 2.3.4 去重

- 按 `invoice_number` 去重（主要）
- 无发票号时按 `金额 + 日期 + 销售方` 复合键去重

---

### 2.4 行程单处理（打车场景）

#### 2.4.1 输入

- 打车发票 PDF（含总金额）
- 打车行程单 PDF（含各行程明细）

#### 2.4.2 处理流程

```
行程单 PDF
  │
  ▼
逐页 OCR → 提取各行程
  │
  ├─ date_time（行程时间）
  ├─ provider（滴滴/高德）
  ├─ pickup（上车点）
  ├─ dropoff（下车点）
  └─ amount（行程金额）
  │
  ▼
汇总金额 = Σ(各行程金额)
  │
  ▼
比对发票金额（允许误差）
  │
  ▼
各行程 → 匹配对应支付订单
```

### 2.5 报销表单生成

#### 2.5.1 报销类别

```
城市间交通费
├── 车、船票（高铁）
├── 飞机票
└── 订（退、改签）票及交通保险费

市内交通费

住宿费

餐补/伙食补助
```

#### 2.5.2 表单内容

| 字段 | 说明 |
|------|------|
| 基本信息 | 姓名、部职别、出差日期、同行人数 |
| 各类别汇总 | 单据张数、申报金额 |
| 支付单号 | 关联的支付交易号 |
| 总计金额 | 所有类别合计 |

#### 2.5.3 输出文件

**文件 1：报销表单 PDF**
- 按类别统计的汇总表
- 含基本信息和总计

**文件 2：发票-支付对照 PDF**

| 发票类型 | PDF 结构 |
|----------|----------|
| 普通发票（高铁/机票/住宿） | 发票页 → 支付记录页 |
| 打车发票 | 发票页 → 行程单页 × N → 行程-支付对照表 |

整体结构：
1. 按类别分组排列
2. 类别顺序：城市间交通 → 市内交通 → 住宿 → 其他
3. 末页：汇总页（各类别张数、金额、总计）

## 4. 数据模型

### 4.1 Invoice（发票）

```rust
struct Invoice {
    id: String,                    // UUID
    invoice_number: String,        // 发票号码
    amount: f64,                   // 金额
    seller_name: String,           // 销售方名称
    item_name: String,             // 项目名称
    date: NaiveDate,               // 开票日期
    category: InvoiceCategory,     // 分类
    source: InvoiceSource,         // 来源（照片/PDF/链接）
    itineraries: Vec<Itinerary>,   // 行程明细（打车场景）
}
```

### 4.2 PaymentRecord（支付记录）

```rust
struct PaymentRecord {
    id: String,                    // UUID
    transaction_id: String,        // 交易单号
    transaction_time: String,      // 交易时间
    amount: f64,                   // 交易金额
    merchant_name: String,         // 商户名称
    source: PaymentSource,         // 来源（微信/支付宝）
    category: String,              // 交易类型
}
```

### 4.3 MatchResult（匹配结果）

```rust
struct MatchResult {
    invoice_id: String,
    invoice: Invoice,
    payment_ids: Vec<String>,
    payments: Vec<PaymentRecord>,
    match_type: MatchType,         // OneToOne / OneToMany / Unmatched / ManualConfirmed
    confidence: f64,               // 置信度 0-1
    amount_diff: f64,              // 金额差异
}
```

### 4.4 ReimbursementForm（报销表单）

```rust
struct ReimbursementForm {
    name: String,                  // 姓名
    department: String,            // 部职别
    travel_start: String,          // 出差开始日期
    travel_end: String,            // 出差结束日期
    companions: usize,             // 同行人数
    summaries: Vec<CategorySummary>, // 各类别汇总
    total_amount: f64,             // 总计
}
```

## 7. 约束与限制

### 7.1 已知限制

- OCR 对手写体、模糊图片识别率较低
- 暂不支持批量 PDF 直接识别（需逐页转图片）
- 行程单解析依赖固定格式（滴滴/高德）

### 7.2 后续扩展

- [ ] 多报销模板支持
- [ ] 历史报销记录查询
- [ ] 批量处理优化
