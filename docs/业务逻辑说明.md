# 发票报销助手 — 业务逻辑说明（与当前代码对齐）

> 本文档描述当前 `src-tauri/src/` 下的实际实现。行号会随迭代变化，具体以源码为准。

---

## 1. 文件导入入口

### 1.1 `batch_global_import(dir_paths)`（`src-tauri/src/lib.rs`）

**内部逻辑：**
1. 接收一个或多个目录路径，递归收集所有文件（`collect_files_recursive`）
2. 按扩展名分流：
   - `.pdf` → 先收集到 `pdf_files`，最后统一调用 `parse_all_from_files`
   - `.jpg/.jpeg/.png` → 调用 `parse_invoice_from_image` 解析为发票
   - `.xlsx/.xls` → 调用 `parse_wechat_bill` 解析为支付记录
   - `.csv` → 调用 `parse_alipay_bill` 解析为支付记录
3. PDF 批量解析后合并 invoices、payments、errors
4. 对合并后的全部发票再做一次批次内去重（覆盖图片之间、图片与 PDF 之间重复）

### 1.2 `collect_files_recursive(dir)`

- 递归遍历目录，只收集普通文件，不处理符号链接等
- 与 `collect_files(paths, extensions)` 命令配合，支持按扩展名过滤

### 1.3 `batch_recognize(file_paths)` / `recognize_invoice(file_path, file_type)`

- `batch_recognize` 调用 `parse_all_from_files`，批量解析 PDF（发票+行程单）并自动配对
- `recognize_invoice` 根据 `file_type`（`pdf`/`image`）分发到 `parse_invoice_from_pdf` 或 `parse_invoice_from_image`

## 2. PDF 文本提取与文档类型判断

### 2.1 pdfplumber 提取（`text_extractor.rs`）

- `classify_pdf_document_type(text_items)`：优先级为 `行程单 > 结账单 > 发票 > Unknown`
- `has_sufficient_text(items, min_chars)`：字符总长度 >= 阈值（发票/行程单场景 20）才认为文字型 PDF
- `is_garbled_text` / `is_garbled_items`：检测 CID 字体乱码（韩文音节、PUA、替换符、控制字符等），乱码比例 >= 0.3 时判定为乱码并回退 OCR
- `extract_pdf_column_aware` / `extract_pdf_column_aware_with_norm`：pdfplumber 列感知提取，返回按页文本、word 级文本、原始 words、表格结构
- `extract_text_with_coords_flat`：提取带坐标的 `OcrTextItem` 列表，供行程单/发票回退解析
- `extract_raw_words_debug`：调试接口，返回原始 word 及坐标

### 2.2 解析流水线（`invoice_pipeline.rs`）

#### `parse_invoice_from_pdf(pdf_path, engine, config)`

实际主路径为 **pdfplumber 表格单元格提取**：

1. 调用 `extract_pdf_column_aware(pdf_path)`
2. 无表格结构、pdfplumber 失败、或文字乱码时 → 回退 OCR 后 `check_and_parse`
3. 非发票类型（行程单/结账单）→ 报错
4. 用 `cell_extractor::extract_fields_from_tables` 提取 seller/amount/item/remarks 等
5. 若单元格未提取到 seller 或 amount（如无框线火车票）→ 回退 `parse_invoice_text`（word 级文本），火车/机票再尝试 char 级重建出行日期
6. 成功则用 `build_invoice_from_cells` 构建发票：发票号/日期从全文正则提取，住宿/票据城市/通行时间等按类别补充

#### `parse_invoice_from_image(image_path, engine)`

1. `engine.recognize_image`
2. `check_and_parse`：先 `classify_pdf_document_type`，非发票返回错误，否则 `parse_invoice_text`

#### `extract_text_with_coords_or_fallback(pdf_path, engine)`

- 优先 pdfplumber 带坐标文本，满足 `has_sufficient_text && !is_garbled_items` 时直接返回
- 否则回退 OCR 文本

### 2.3 行程单解析流水线（`parse_itinerary_from_pdf`）

1. 优先 `extract_pdf_column_aware_with_norm(pdf_path, true)`（行程单开启列网格归一化）
2. 文字足够且类型为行程单/发票时：
   - 先 `parse_itinerary_from_tables` 用 find_tables 单元格解析
   - 成功且无缺失字段 → 补年份、交叉验证后返回
   - 否则按页 word 级坐标解析 → 纯文本 → OCR 坐标逐级回退
3. pdfplumber 不可用/文字不足 → OCR 路径
4. 最后 `build_itinerary_doc`：提取印制合计金额（`extract_itinerary_printed_total`），有则用合计金额交叉验证并按合计金额作为 `total_amount`；否则累加行程金额

## 3. 发票解析与分类（`invoice_parser.rs`）

### 3.1 `parse_invoice_text(texts, source)`

**内部逻辑：**
1. 检测竖排标题（`detect_vertical_titles_from_items`），合并竖排单字
2. 按坐标排序、全角数字归一化、行分组重建
3. `split_into_regions` 切分为 header/buyer/seller/items/total/remarks
4. 提取字段：
   - 金额：`extract_amount(regions.total)`，失败回退 `extract_amount(all_text)`
   - 销售方：`extract_seller_name(regions.seller)` → 竖排标题定位 → 坐标最右「名称：」→ 全文；仍异常时用公司名后缀回退
   - 项目名称：`extract_item_name(regions.items)`
   - 开票日期：`extract_date(all_text)`
   - 发票号码：`extract_invoice_number(regions.header)`
5. 分类：`classify_from_regions`，若为 `Other` 再走 `classify_from_full_text`
6. 住宿发票：综合备注天数、商品数量、结账单日期交叉验证得到 `hotel_detail`
7. 火车/机票：提取 `departure_city` / `arrival_city` / `travel_date`
8. 高速通行费：备注为空时用坐标恢复备注，再提取 `toll_travel_time`

### 3.2 `split_into_regions(text)`

- 按行扫描，状态机切换区域；`past_total` 后只允许进入备注
- 备注区域一旦进入不再跳出

### 3.3 `extract_amount(text)`

多步回退，强制要求两位小数，排除税号/整数误匹配：
1. 数字在“价税合计”前（跳过税额行）
2. “价税合计/合计金额/总金额 + ¥ + 两位小数”
3. 关键字后 10 字符内两位小数
4. “合计 XXX.XX 元”（行程单）
5. 区域内裸两位小数取最大值
6. 全文 ¥ 金额取最大值（排除 >= 1,000,000）

### 3.4 `extract_seller_name(text)`

- 精确匹配“名称：…”取最后一个（卖方通常在买方后）
- 兼容 CJK 空格，收集候选并过滤买方关键词
- 回退“销售方/收款单位/开票方”

### 3.5 `extract_seller_by_coords(texts)` / `extract_seller_by_vertical_title`

- 坐标版：匹配“名称：”块，取 X 中心最大的块（最右侧）
- 竖排标题版：定位“销售方信息”竖排标题，收集其右侧同 Y 区域文本后提取

### 3.6 其他字段提取

- `extract_item_name`：`*服务类型*` 或“项目名称/货物或应税劳务/商品名称”
- `extract_date`：支持 `YYYY年M月D日`、`YY年M月D日`（补 2000）、`YYYY-MM-DD`
- `extract_invoice_number`：支持正常、CJK 空格、反向、反向空格四种模式

### 3.7 分类逻辑

#### `classify_from_regions(items_text, seller_text, item_name, seller_name)`

优先级：
1. 税收编码：`*住宿服务*` / `*生产生活服务*住宿费` → Hotel；`*运输服务*`/`*客运服务*` 按火车/机票/市内交通细分；`*航空运输服务*`/`*旅客运输服务*` → Flight；`*餐饮服务*` → Meal
2. 商品名称关键词（含保险优先）
3. 商品区域全文回退
4. 销售方名称关键词
5. 销售方区域全文回退

#### `classify_from_full_text(ocr, invoice_type)`

- 同样先税收编码
- 保险优先于 Flight
- 按 `InvoiceTypeDetector` 结果（Flight/Train/Hotel/RideHailing/Toll）短路
- 再按全文关键词回退

#### `classify_invoice(seller_name, item_name)`

简易分类，供前端/旧路径使用；关键词顺序为 Train → Insurance → TicketChange → Flight → CityTransport → Hotel → Toll → Meal → Other。

### 3.8 住宿详情

- `parse_hotel_detail(remarks, invoice_date)`：匹配 `M-DD至M-DD`，跨年推断年份，`nights = check_out - check_in`
- `parse_nights_from_remarks(remarks)`：`共N天`
- `extract_item_quantity(items_text)`：从商品明细行提取数量（`q>1` 才作为住宿晚数参考）
- `extract_hotel_statement_detail(all_text, date)`：从结账单文本提取入住/离店

## 4. 发票类型检测（`invoice_type_detector.rs`）

`InvoiceTypeDetector::detect(ocr_output)` 的检测顺序：

1. `RideHailingItinerary`：行程报销单，或“行程单”+滴滴/高德/T3/曹操
2. `TransitCardStatement`：天府通，或“电子行程单”+公交/地铁
3. `FlightInvoice`：机票/航班/航空，或“行程单”+飞猪/携程/去哪儿（排除保险）
4. `TollInvoice`：通行费/过路费/ETC+高速/高速+电子发票
5. `VatElectronicInvoice`：增值税+电子发票，或电子普通发票且非网约车
6. `HotelStatement`：结账单/账单 + 酒店
7. `TrainInvoice`：火车票/铁路客票/高铁/车次号+站
8. `RideHailingInvoice`：滴滴/高德/T3/曹操且不含“行程单”
9. `Other`

额外处理 CJK 部首变体（如“电⼦发票” U+2F26 → “子”）。

## 5. 行程单解析（`itinerary_parser.rs`）

### 5.1 纯文本解析 `parse_itinerary_text(texts)`

依次尝试：
1. OCR 带 ¥ 格式：`YYYY-MM-DD HH:MM 服务商 ¥金额`
2. 表格/纯文本格式：`序号 车型 MM-DD HH: 城市 ... 里程 金额`，支持续行分钟
3. 天府通格式（`parse_tianfutong_format`）
4. 兜底 ¥ 金额 + 独立数字行

解析后统一 `enrich_itinerary_years` 补年份。

### 5.2 坐标解析 `parse_itinerary_with_coords_pages_and_fallback(pages, fallback_texts)`

- 按页调用 `parse_itinerary_with_coords`
- 每页从 `box_coords` 提取中心坐标，生成 `PositionedText`
- 有效块 < 4 时回退纯文本
- 所有页结果非空时，用 fallback 文本做 `cross_validate_amounts` + `enrich_itinerary_years`
- 否则回退纯文本

### 5.3 通用表格解析 `parse_table_generic`

1. `find_header`：定位“序号”行，收集表头块
2. `COL_KEYWORDS` 映射语义列（Seq/Time/Pickup/Dropoff/Amount/Provider/City）
3. `build_col_boundaries`：由表头块 X 坐标计算列边界
4. 锚点构建：序号锚点 + 时间锚点 + 间隔填充（gap > 1.8×行高补金额锚点）
5. 主行/续行分离：主行 `|y - anchor.y| <= 0.3×行高`，续行在锚点下方到下一锚点中点
6. 逐列收集文本：时间清洗、金额合并列分割（里程+金额同一表头时只用 X>header_x）、起点/终点拼接、车型过滤
7. 时间正则支持多种 OCR 粘连格式
8. 按 `(date_time, round(amount*100))` 去重

### 5.4 `parse_itinerary_from_tables`

- 使用 pdfplumber find_tables 单元格文本直接构建行程
- 若结果完整则优先返回，否则回退坐标/文本解析

### 5.5 交叉验证

#### `cross_validate_amounts(entries, fallback_texts)`

- 金额：从参考文本行尾提取金额，数量一致时按位置覆盖差异 >0.005 的值
- 服务商：主行服务商 + 续行后缀合并，覆盖空/纯数字/单字符/前缀截断
- 时间：从参考文本提取日期+小时+分钟，覆盖乱码时间

#### `cross_validate_with_printed_total(entries, printed_total)`

- 当行程金额累加与印制合计差异 >=0.5 元时，按比例分摊差额

#### `extract_itinerary_printed_total(texts)`

- 支持“合计 XXX.XX 元”、“合计金额：XXX.XX”、“合计：XXX.XX”

### 5.6 行程-发票配对 `pair_invoices_with_itineraries`

- 有印制合计金额：精确匹配 `|inv.amount - total_amount| <= 0.01`
- 无印制合计：容差匹配（当前调用方传 2.00）
- 匹配成功：发票类别设为 `CityTransport`，写入 `itineraries` 和 `itinerary_file`
- 未匹配：创建虚拟市内交通发票

## 6. 支付账单导入

### 6.1 `parse_wechat_bill(file_path)`（`wechat_parser.rs`）

1. `calamine::open_workbook_auto` 打开 xlsx，取第一个工作表
2. 找到“交易时间”标题行后开始
3. 每行解析：交易时间、交易类型、商户名称、分类、收/支、金额、支付方式、状态、交易单号、备注（备注在第 11 列，index 10）
4. `cell_to_string` 处理 DateTime/序列号/字符串
5. 金额与退款/优惠：
   - `extract_refund_amount(status)`：从状态提取退款金额
   - `extract_discount_amount(remark)`：从备注提取优惠金额
   - “收入+退款”记为负；“支出+全额退款”跳过；“支出+部分退款”净额 = 原支付 - 退款
6. 净额 <0.01 跳过

### 6.2 `parse_alipay_bill(file_path)`（`alipay_parser.rs`）

1. GBK 解码文件
2. 第一遍收集原始记录（交易时间、类型、商户、金额、支付方式、交易单号）
3. 第二遍建立退款映射：退款单号 `原始单号*后缀`，按前缀聚合退款金额
4. 第三遍输出：退款记录本身不输出；全额退款跳过；部分退款 `final_amount = 原金额 - 退款总额`

### 6.3 `parse_bill_auto(file_path)`

- 按文件内容嗅探：含“交易单号/商户单号” → 微信；含“商家订单号/支付宝” → 支付宝
- 无法嗅探时按扩展名：csv → 支付宝，其余 → 微信

### 6.4 `PaymentRecord::total_value()`

```rust
(self.amount - self.refund_amount).max(0.0) + self.discount
```

- `is_refund()`：`refund_amount > 0 || amount <= 0`

## 7. 发票-支付匹配引擎（`matching/`）

### 7.1 `MatchEngine`

- `new(tolerance)`，默认 1.00
- `match_one_to_one`：
  - 参考日期优先级：`travel_date` → `toll_travel_time.date()` → `hotel_detail.check_in` → `invoice.date`
  - 金额差取 `|amount - total_value()|` 与 `|amount - amount|` 较小者，须 <= tolerance
  - 候选按“与参考日期天数差”优先，天数相同按金额差
- `match_one_to_many`：
  - 候选过滤 `p.amount <= target + tolerance`，最多 20 笔
  - 子集搜索 `search_subset` 找到金额差最小的最优子集，子集上限 10

### 7.2 `batch_match_with_progress`（实际批量入口）

1. 支付按交易时间升序排序，过滤退款交易
2. 分离 Toll 发票与其余发票
3. 第一阶段：高速费单独一对一匹配；失败进入待关联
4. 第二阶段：待关联高速费按通行时间找最近的 CityTransport，用“行程发票金额 + 高速费金额”组合匹配；成功时生成行程 MatchResult 和高速费共享 MatchResult（`shared_payment_ids` / `shared_from_invoice_id`）
5. 第三阶段：剩余非高速费发票按金额降序处理：
   - CityTransport 带行程 → `match_itinerary_to_payments`，失败回退按行程时间过滤后 `match_one_to_many`
   - Insurance → 使用同批次机票窗口的 4 级匹配（精确时间戳 → 机票窗口 → 出行时间上界 → 硬过滤）
   - 其他 → 先 `filter_payments_by_date_direction`（支付日期 <= 开票日期），再按 `StrategySelector` 选择策略
6. 未匹配的 CityTransport 单行程尝试 toll_best 容差（支付 > 行程金额且同日/次日凌晨）

### 7.3 `match_itinerary_to_payments`

- 第 1 轮宽容匹配：按行程 provider 优先找对应商户，统计出现最多的商户作为 `real_merchant`
- 第 2 轮精确锁定：只用 `real_merchant` 的支付重新匹配，任一行程失败则整体失败
- 生成 `itinerary_payment_pairs` 显式记录行程→支付

### 7.4 `StrategySelector::select`

- CityTransport 且有行程 → `OneToMany`
- seller_name 非空 → `AmountWithMerchant`
- 否则 → `MultiDimensional`

### 7.5 `MultiDimensionalScorer`

- 权重：金额 0.4 / 商户 0.3 / 时间 0.2 / 类别 0.1
- `score_amount`：差额 <=5 线性衰减到 0.5，超过为 0
- `score_merchant`：相等 1.0，包含 0.9，Levenshtein >0.7 返回相似度，否则品牌关键词 0.85
- `score_time`：按天数差 0/1/3/7 分档，无法解析 0.5
- `score_category`：按类别关键词命中 1.0，Other 0.5

### 7.6 分趟 `segment_trips`

- `origin=None` 自动分趟：按票据城市与日期聚合成 `TripGroup`
- `origin=Some(城市)`：以指定出发城市全量重分
- 支持人工归趟（前端）

## 8. 报销单计算（`form_builder.rs`）

`build_reimbursement_form(match_results, name, department, destination, travel_start, travel_end, companions, hotel_level)`

1. `travel_days = days_between(start, end)`（包含首尾，至少 1）
2. 伙食补助标准：`reimbursement_config::meal_subsidy_daily()`（默认 100）
3. 市内交通日标准：`reimbursement_config::city_transport_daily()`（默认 80）
4. 住宿标准：`get_hotel_nightly_rate_std(destination)`
5. 城市间交通费：Train/Flight/Insurance/TicketChange 四类明细 + 小计
6. 市内交通费：CityTransport + Toll 合并张数与金额，`min(实际, 日标准 × travel_days)`
7. 住宿费：每张 Hotel 发票按 `hotel_detail.nights`（缺失时 `travel_days-1` 估算），`min(实际, 每晚标准 × nights)` 封顶
8. 伙食补助：`travel_days × 日标准`
9. `total_amount = 非市内/非高速发票可报销金额 + 市内封顶金额 + 伙食补助`

## 9. 住宿标准（`hotel_standard.rs` + `reimbursement_config.rs`）

### 9.1 数据源

- 内置标准：`data/住宿标准.xlsx`（缺失时使用硬编码默认表）
- 城市→省份映射：编译时嵌入 `data/参考数据/cities.json`、`data/参考数据/provinces.json`
- 用户配置：`reimbursement-config.json`（标准集，含省份默认 + 城市细分）

### 9.2 匹配逻辑 `get_hotel_nightly_rate_std(destination)`

- 激活用户标准集时：
  1. 直接匹配用户集条目
  2. 城市关键词 → 省份匹配
  3. 回退用户集 `default_hotel_standard`
- 未激活用户集（内置）：
  1. 直接匹配内置规则
  2. 城市关键词 → 省份匹配
  3. 回退 350

### 9.3 `extract_city_keyword`

- 去掉“市/区/县/自治州/地区”后缀，取最后 2~4 个字符作为候选

## 10. 数据去重（`dedup.rs`）

- 有发票号：按 `invoice_number` 去重
- 无发票号：按 `金额_日期_销售方` 组合键去重
- 保留首次出现，返回重复发票号列表

## 11. 输出生成（`pdf/`）

### 11.1 报销表单

- `form_html_generator`：生成完整 HTML 报销单（含中文大写金额）
- `form_generator`：生成 PDF 报销单
- `form_xlsx_generator`：生成 XLSX 报销单
- `amount_to_chinese`：人民币大写转换

### 11.2 发票-支付对照

- `comparison_generator`：基础 PDF 对照
- `comparison_image_pdf_generator`：用 `medpdf` 生成含票据影像的 A4 横向 PDF
- `comparison_html_generator`：HTML 对照（含图片）
- `comparison_xlsx_generator`：完整信息 Excel 对照

### 11.3 图片渲染

- `image_embedder::render_pdf_to_rgb_images`：使用 zpdf 纯 Rust 渲染 PDF 页面为 RGB 图片（RGBA→RGB），无需 pdfium.dll
- `render_pdf_page_to_png` / `render_pdf_all_pages_to_pngs`：输出 PNG 供预览/对照/调试使用

---

## 12. OCR 引擎（`ocr/engine.rs`）

- `OcrEngine::new(models_dir)`：
  - 需要 `PP-OCRv5_mobile_det.mnn`、`PP-OCRv5_mobile_rec.mnn`、`ppocr_keys_v5.txt`
  - 模型缺失时返回 `uninitialized()`，应用仍可运行（文本 PDF 不受影响）
- `recognize_image` / `recognize_rgb_image`：图片 OCR，输出 `OcrTextItem { text, confidence, box_coords }`
- `recognize_pdf`：
  - 先用 zpdf 渲染 PDF 为图片，再逐页 OCR
  - zpdf 失败时回退 `pdftoppm`（需 poppler-utils）
- `process_to_structured`：过滤低置信度，输出结构化块/布局（供类型检测使用）
- `model_downloader`：从可配置 GitHub Releases 基址下载 3 个模型文件，支持热替换引擎
