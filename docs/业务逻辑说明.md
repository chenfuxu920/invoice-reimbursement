# 发票报销助手 — 完整业务逻辑说明（含方法内部逻辑）

> **注意**：本文档中的行号引用基于撰写时的代码快照，随代码迭代可能已偏移。关键逻辑描述仍然准确，具体行号请以源码为准。

## 1. 文件导入入口

### 1.1 `batch_global_import(dir_path)` — 全局导入（lib.rs:263-330）

**内部逻辑：**
1. 调用 `collect_files_recursive(dir)` 递归遍历目录，收集所有文件（支持子目录嵌套）
2. 按扩展名分流处理：
   - `.pdf` → 暂存到 `pdf_files` 列表，全部收集完后统一调用 `parse_all_from_files`
   - `.jpg/.jpeg/.png` → 逐个调用 `parse_invoice_from_image`
   - `.xlsx/.xls` → 调用 `parse_wechat_bill`，解析结果追加到 payments
   - `.csv` → 调用 `parse_alipay_bill`，解析结果追加到 payments
3. PDF 文件统一处理后，invoices + payments + errors 合并返回

### 1.2 `collect_files_recursive(dir)`（lib.rs:247-260）

**内部逻辑：**
- 打开目录迭代器，对每个条目
- 是目录 → 递归调用自身
- 是文件 → 收集到 Vec<PathBuf>
- 不处理符号链接等其他类型

### 1.3 `batch_recognize(file_paths)` 和 `recognize_invoice(file_path, file_type)`

- `batch_recognize` 接收文件路径列表，调用 `parse_all_from_files`
- `recognize_invoice` 根据 file_type（image/pdf）分发到 `parse_invoice_from_image` 或 `parse_invoice_from_pdf`

## 2. PDF 文本提取与文档类型判断

### 2.1 `extract_text_from_pdf(file_path)`（text_extractor.rs:52-79）

**内部逻辑（三段式降级）：**
1. **优先 parangi**：调用 `parangi::extract_text(path)`，如果返回非空文本列表则直接返回
2. **回退 pdf-extract**：当 parangi 返回空或失败时，用 `std::panic::catch_unwind` 包裹 `pdf_extract::extract_text(file_path)` 防止 panic 崩溃
3. **最终降级**：如果 pdf-extract 也失败或 panic，返回 Err，上层会回退到 OCR
4. 提取结果通过 `text_to_items` 将每行文本转为 `OcrTextItem{ text, confidence: 1.0 }`

### 2.2 `text_to_items(text)`（text_extractor.rs:81-91）

**内部逻辑：**
- 按行分割 `text.lines()`
- 每行 `trim()`，过滤空行
- 每行转为 `OcrTextItem { text, confidence: 1.0, box_coords: None }`

### 2.3 `has_sufficient_text(items, min_chars)`（text_extractor.rs:95-98）

**内部逻辑：**
- 计算所有 `items[i].text.len()` 的总和
- 判断是否 >= min_chars（发票解析场景 min_chars=20）
- <20 字符认为文字提取失败，回退 OCR

### 2.4 `classify_pdf_document_type(text_items)`（text_extractor.rs:20-46）

**内部逻辑（优先级从高到低）：**
1. 全文拼接为字符串
2. 含 "行程单" / "行程报销单" / "电子行程单" → `Itinerary`
3. 含 "结账单" → `Bill`
4. 含 "发票" / "增值税" → `Invoice`
5. 以上都不满足 → `Unknown`

### 2.5 `parse_invoice_from_pdf(pdf_path, engine)`（invoice_pipeline.rs:24-38）

**内部逻辑（双路径 + OCR 回退）：**
1. 包装 source = `InvoiceSource::Pdf(pdf_path)`
2. 调用 `extract_text`（内部先 parangi/pdf-extract 提取文字，文字不足则 OCR）
3. 调用 `check_and_parse` 解析
4. **如果解析成功但 seller_name 为空**：认为 parangi 文字提取乱序（多列布局导致），回退到 OCR 重新解析
5. **如果解析失败**（如金额无法识别）：同样回退到 OCR 重新解析
6. OCR 回退路径：`extract_ocr_text` → 逐页 OCR 识别 → 合并为 `Vec<OcrTextItem>` → 再次调用 `check_and_parse`

### 2.6 `parse_invoice_from_image(image_path, engine)`（invoice_pipeline.rs:41-45）

**内部逻辑：**
1. 包装 source = `InvoiceSource::Photo(image_path)`
2. 调用 `engine.recognize_image(image_path)` 进行 OCR
3. 调用 `check_and_parse` 检查文档类型，然后调用 `parse_invoice_text` 解析

### 2.7 `check_and_parse(text_items, source)`（invoice_pipeline.rs:47-56）

**内部逻辑：**
1. 调用 `classify_pdf_document_type(&text_items)` 判断文档类型
2. 如果不是 `Invoice` 类型，返回 `Err("非发票类型")`
3. 是发票类型，调用 `parse_invoice_text(&text_items, source)`

## 3. 发票解析与分类（核心）

### 3.1 `split_into_regions(text)` — 发票区域分割（invoice_parser.rs:27-91）

**内部逻辑（逐行扫描 + 状态机）：**
```
初始区域 = "header"
遍历每行（trimmed）：
  ├── 含 "购买方" + ("名称" or "统一社会信用代码") → 切换到 buyer 区域
  ├── 含 "销售方" → 切换到 seller 区域
  ├── 含 "项目名称" / "货物或应税劳务" → 切换到 items 区域
  ├── 含 "价税合计" / "票价" / "合计金额" → 切换到 total 区域
  ├── 含 "备注" 且不含 "：" → 切换到 remarks 区域
  └── 当前区域追加文本 + 空格
```
返回 `InvoiceRegions { header, buyer, seller, items, total, remarks }`

### 3.2 `parse_invoice_text(texts, source)` — 传统文本解析入口（invoice_parser.rs:93-169）

**内部逻辑：**
1. 所有 OcrTextItem 用换行符拼接为 `all_text`
2. `split_into_regions(&all_text)` 切分为 6 个区域
3. 从各区域提取字段：
   - `extract_amount(&regions.total)` — 金额（先尝试 total 区域，失败则回退到全文搜索）
   - `extract_seller_name(&regions.seller)` — 销售方名称（先尝试 seller 区域正则，失败则用坐标最右侧"名称："块）
   - `extract_item_name(&regions.items)` — 项目名称
   - `extract_date(&all_text)` — 开票日期
   - `extract_invoice_number(&regions.header)` — 发票号码
4. `classify_from_regions(...)` 基于区域做首次分类
5. 如果分类为 `Other`，降级到 `classify_from_full_text` 做二次分类
6. 如果是 Hotel 类别，解析住宿详情
7. 构建并返回 `Invoice`

### 3.3 `extract_amount(text)` — 金额提取（invoice_parser.rs:549-575）

**内部逻辑（四级回退）：**
1. **精确标签匹配**：正则 `(?:价税合计|合计金额|总金额|金额)[：:￥¥]*\s*([\d,]+\.?\d*)`，找到第一个匹配值
2. **行程单合计**：正则 `合计\s*([\d,]+\.?\d*)\s*元`
3. **通用 ¥ 匹配**：正则 `[￥¥]\s*([\d,]+\.?\d*)`，遍历所有匹配，取最大值
4. 以上均失败 → `Err("无法识别发票金额")`
5. **调用方回退**（`parse_invoice_text`）：如果 total 区域提取失败，用全文 `all_text` 重新调用 `extract_amount`

### 3.4 `extract_seller_name(text)` — 销售方名称提取（invoice_parser.rs:577-592）

**内部逻辑（两级回退）：**
1. 正则 `名称[：:]\s*(.+?)(?:\s+统一社会信用代码|\s+$)`，长度 >2 才接受
2. 回退正则 `(?:销售方|收款单位|开票方)[：:]\s*(.+?)(?:\s|$)`
3. 均失败 → 返回空字符串

### 3.4b `extract_seller_by_coords(texts)` — 坐标感知销售方提取（invoice_parser.rs:597-615）

**触发条件**：`extract_seller_name` 返回空时调用

**内部逻辑**：
1. 遍历所有 OcrTextItem，正则 `名称[：:]\s*(\S.+)` 匹配包含 "名称：" 的块
2. 从 `box_coords.points[0].x` 提取 X 坐标
3. 取 X 坐标最大的块（最右侧 = 销售方侧），提取公司名
4. 增值税发票布局：左列（购买方）X≈400，右列（销售方）X≈1300

### 3.5 `extract_item_name(text)` — 项目名称提取（invoice_parser.rs:594-607）

**内部逻辑：**
1. 正则 `\*(.+?)\*` 匹配 `*服务类型*` 格式（税收编码）
2. 回退正则 `(?:项目名称|货物或应税劳务|商品名称)[：:]\s*(.+?)(?:\s|$)`
3. 均失败 → 空字符串

### 3.6 `extract_date(text)` — 日期提取（invoice_parser.rs:609-625）

**内部逻辑：**
1. 正则 `(\d{4})\s*年\s*(\d{1,2})\s*月\s*(\d{1,2})\s*日` — 中文格式
2. 正则 `(\d{4})-(\d{2})-(\d{2})` — ISO 格式
3. 捕获组解析为 `NaiveDate`，解析失败用默认值
4. 均不匹配 → `NaiveDate::default()`（即 0001-01-01）

### 3.7 `extract_invoice_number(text)` — 发票号码提取（invoice_parser.rs:627-640）

**内部逻辑：**
1. 正则 `(?:发票号码|No)[：:]\s*(\d+)` — 正常标签在前
2. 正则 `(\d{8,20})\s*发票号码` — 反向模式（PDF 文字提取时号码出现在标签之前）
3. 均失败 → 空字符串

### 3.8 住宿发票详情解析

#### `parse_hotel_detail(remarks, invoice_date)`（invoice_parser.rs:173-194）

**内部逻辑：**
1. 正则 `订单日期[:：]?\s*(\d{1,2})-(\d{1,2})\s*至\s*(\d{1,2})-(\d{1,2})`
2. 提取入住月份、日、离店月份、日
3. 以发票日期的年份构造 `NaiveDate`
4. 计算 `nights = (check_out - check_in).num_days().max(1)`
5. `nightly_rate` 设为 0.0（后续由 form_builder 计算）

#### `parse_nights_from_remarks(remarks)`（invoice_parser.rs:197-201）

**内部逻辑：**
- 正则 `共(\d+)天` 从备注提取住宿天数

#### `extract_item_quantity(items_text)`（invoice_parser.rs:204-208）

**内部逻辑：**
- 正则 `\*住宿服务\*.*?\s+(\d+)\s+[\d,.]+` 从商品明细行提取数量
- 匹配 "*住宿服务*住宿费  1  420.00" 中的 1

### 3.9 `classify_from_regions(...)` — 基于区域的分类（invoice_parser.rs:212-295）

**内部逻辑（5 层优先级递进）：**

**第 1 层：税收编码匹配（最可靠）**
- `items_text` 含 `*住宿服务*` → Hotel
- `*运输服务*`/`*客运服务*` → 检查 `items_lower` 含 "火车"/"高铁"/"铁路" → Train；含 "航空"/"机票" → Flight；否则 → CityTransport
- `*航空运输服务*`/`*旅客运输服务*` → Flight
- `*餐饮服务*` → Meal

**第 2 层：商品名称关键词**（从 items 区域提取的 item_name）
- 住宿/酒店/宾馆/民宿 → Hotel
- 机票/航空/航班 → Flight
- 火车/高铁/铁路 → Train
- 餐饮/饭店/餐厅 → Meal

**第 2.5 层：商品区域全文回退**（item_name 可能提取失败）
- 机票/航空/航班/旅客运输 → Flight
- 退票/改签/手续费 → TicketChange
- 火车/高铁/铁路 → Train
- 住宿/酒店/宾馆 → Hotel

**第 3 层：销售方名称关键词**
- 滴滴/高德/网约车/T3/曹操 → CityTransport
- 酒店/宾馆/住宿 → Hotel
- 航空/机票 → Flight
- 铁路/高铁/火车 → Train

**第 3.5 层：销售方区域全文回退**
- 航空/机票 → Flight
- 铁路/高铁/火车 → Train

**都不匹配 → Other**

### 3.10 `classify_from_full_text(...)` — 基于全文的分类（invoice_parser.rs:466-547）

**内部逻辑（7 层优先级）：**

**第 1 层：税收编码匹配**（同上）

**第 2 层：InvoiceType 推断**
- FlightInvoice → Flight
- TrainInvoice → Train
- HotelStatement → Hotel
- RideHailingInvoice / RideHailingItinerary → CityTransport

**第 3 层：全文关键词**
- 酒店/宾馆/住宿/招待所/民宿 → Hotel
- 滴滴/网约车/高德/T3/曹操/出租 → CityTransport
- 航空/机票/机场/航班 → Flight
- 铁路/高铁/火车/客运站 → Train
- 餐饮/饭店/食品/餐厅/饭馆 → Meal
- 退票/改签/保险 → TicketChange

**第 4 层：seller 提取字段**
- 酒店/宾馆/住宿 → Hotel
- 滴滴/高德/网约车 → CityTransport

**第 5 层：item 提取字段**
- 住宿/房费 → Hotel
- 交通/打车/出行 → CityTransport

**都不匹配 → Other**

### 3.11 `classify_invoice(seller_name, item_name)` — 简易分类（invoice_parser.rs:642-664）

**内部逻辑：**
- 拼接 `seller_name + " " + item_name`，全小写
- 关键词依次检查：铁路/高铁/火车/客运站 → Train；航空/机票/机场/航班 → Flight；退票/改签/保险 → TicketChange；出租/网约车/滴滴/高德/T3/曹操 → CityTransport；酒店/宾馆/住宿/招待所/民宿 → Hotel；餐饮/饭店/食品/餐厅/饭馆 → Meal；否则 → Other

## 4. 发票类型检测（InvoiceTypeDetector）

### 4.1 `InvoiceTypeDetector::detect(ocr_output)`（invoice_type_detector.rs:20-57）

**内部逻辑：**
1. 所有 block 文本拼接为字符串
2. 按固定优先级依次调用 7 个检测方法，命中即返回：
   - `is_ride_hailing_itinerary`：含 "行程报销单" 或（"行程单" + （"滴滴" / "高德" / "T3" / "曹操"））
   - `is_transit_card_statement`：含 "天府通" 或（"电子行程单" + （"公交" / "地铁"））
   - `is_flight_invoice`："机票" / "航班" / "航空" / （"行程单" + （"飞猪" / "携程" / "去哪儿"））
   - `is_vat_electronic_invoice`："增值税" + "电子发票"
   - `is_hotel_statement`：（"结账单" / "账单"） + "酒店"
   - `is_train_invoice`："火车票" / "铁路客票" / "铁路电子客票" / "高铁" / （车次号 `[GD]\d+` + （"站" / "铁路"））
   - `is_ride_hailing_invoice`：（"滴滴" / "高德" / "T3" / "曹操"） + 不含 "行程单"
3. 均不匹配 → `Other`

## 5. 行程单解析与配对

### 5.1 行程单解析架构

行程单解析采用 **OCR 坐标优先 + 纯文本交叉验证** 的双引擎架构：

```
行程单 PDF
    │
    ├── parangi 纯文本提取 ──► 用于交叉验证（金额/供应商/时间修正）
    │
    └── PDFium + PaddleOCR ──► 带坐标的文本块
                │
                ▼
    parse_itinerary_with_coords (单页)
                │
                ├── find_header ──► 表头识别（序号/时间/起点/终点/金额/车型）
                ├── build_col_boundaries ──► 列边界计算
                ├── 锚点构建（序号 + 时间 + 间隔填充）
                ├── 主行/续行分离（按 Y 坐标分组）
                ├── 逐列文本收集（起点/终点/金额/时间/车型）
                ├── 金额里程列分割（合并表头检测）
                │
                └── cross_validate_amounts ──► 三重交叉验证
                        ├── 金额：OCR 误读 → parangi 修正
                        ├── 供应商：OCR 缺失 → parangi 补全（含续行合并）
                        └── 时间：OCR 乱码 → parangi 恢复（含分钟提取）
```

### 5.2 `parse_itinerary_with_coords(texts)` — OCR 坐标解析入口（itinerary_parser.rs:131-150）

**内部逻辑：**
1. 从每个 OcrTextItem 的 `box_coords` 提取中心坐标 (cx, cy)
2. 过滤空文本，生成 `Vec<PositionedText>`
3. 如果有效块少于 4 个，回退到纯文本解析
4. 调用 `parse_table_generic(&positioned)`，失败回退纯文本

### 5.3 `parse_table_generic(positioned)` — 通用表格解析（itinerary_parser.rs:188-475）

**核心思路**：用序号列做行锚点，动态提取列名及 X 坐标，按行收集各列文本。

#### 步骤 1：表头识别 `find_header`
- 找到包含"序号"的块，取其 Y 坐标
- 收集 Y±20px 范围内的所有块作为表头行
- 验证表头行至少包含"序号"+"时间"或"金额"或"起点"

#### 步骤 2：列映射 `col_map`
- 用 `COL_KEYWORDS` 将表头块的关键词映射到语义列：
  - `序号` → Seq / `上车时间`→ Time / `起点`→ Pickup / `终点`→ Dropoff / `金额`→ Amount / `车型`→ Provider
- `find_col_x` 按关键词长度降序匹配（如"上车时间"优先于"时间"）

#### 步骤 3：列边界计算 `build_col_boundaries`
- 用所有表头块的 X 坐标排序，每列边界 = 相邻表头块的中点
- 支持天 usernames/高德/滴滴等不同列数（5~8 列）

#### 步骤 4：锚点构建（三来源合并）
1. **序号锚点**：X 在 `seq_x ± col_span*0.5` 范围内，且 `is_seq_number` 为 true（过滤含 -、: 的文本和 >200 的数字）
2. **时间锚点**：X 在 `time_x ± col_span*0.5` 范围内，且 `looks_like_datetime` 为 true，且不在已有锚点 `avg_row_h*0.5` 范围内
3. **间隔填充**：连续锚点间隔 > `avg_row_h*1.8` 时，在间隔内找金额块作为合成锚点

#### 步骤 5：主行/续行分离
对每个锚点 Y：
- **主行**：`|block.y - anchor.y| ≤ avg_row_h * 0.3`
- **续行**：`anchor.y + tolerance < block.y < y_hi`
- `y_hi` = 与下一个锚点的中点（最后一行 = `y + avg_row_h * 3`）

#### 步骤 6：逐列收集
- **时间列**：先收集后通过 `clean_time_text` 过滤序号数字
- **金额列**：检测合并列（"里程+金额"在同一表头块时，只用 X > header_x 的右侧数据）
- **起点/终点列**：主行+续行文本拼接
- **车型列**：`filter_provider_blocks` 排除序号、时间、纯数字块，对合并块（如"12专车"）剥离前导数字

#### 步骤 7：时间正则匹配
支持 6 种时间格式：
1. `2026-04-24 17:58:59` — 标准完整格式
2. `2025-09-11 12:11` — 无秒格式
3. `2025-09-1112:11` — 无缝空格合并格式
4. `04-23 19:56` — 短日期格式
5. `04-2319:` — 冒号合并格式
6. `04-2221` — 无冒号乱码格式（OCR 常见）

#### 步骤 8：去重
按 `(date_time, round(amount*100))` 去重

## 9. 发票-支付匹配引擎

### 9.1 `MatchEngine::new(tolerance)`（engine.rs:14-16）

**内部逻辑：**
- 存储一个 `tolerance` 值（默认 1.00 元），表示发票金额和支付金额允许的最大差额

### 9.2 `match_one_to_one(invoice, payments)`（engine.rs:24-51）

**内部逻辑：**
```
对每笔可用支付 payment：
  diff_total = |invoice.amount - payment.total_value()|  // 含优惠的总值
  diff_amount = |invoice.amount - payment.amount|        // 实际支付金额
  diff = min(diff_total, diff_amount)                     // 取较小的差额
  if diff <= tolerance:
    记录为候选，取 diff 最小的为最佳匹配
返回 MatchResult { match_type: OneToOne, confidence: 1.0 - diff/invoice.amount }
```

### 9.3 `match_one_to_many(invoice, payments)`（engine.rs:56-91）

**内部逻辑：**
1. 过滤候选：`p.amount <= invoice.amount + tolerance`，取前 20 笔
2. 调用 `subset_sum_match(target, candidates)` 递归搜索子集
3. 找到子集 → 返回 `MatchResult { match_type: OneToMany, payments: 子集 }`
4. 找不到 → None

### 9.4 `subset_sum_match(target, candidates)`（engine.rs:96-114）

**内部逻辑：**
- 提取候选金额列表 `amounts: Vec<f64>`
- 调用 `search_subset` 进行回溯搜索

### 9.5 `search_subset(amounts, target, start, current_sum, indices, result)`（engine.rs:117-159）

**内部逻辑（带剪枝的回溯）：**
```
每次递归：
  1. 检查 current_sum 与 target 的差额是否在 tolerance 内 → 是则记录结果并返回
  2. 剪枝条件：
     - 子集已达上限 MAX_SUBSET_SIZE(10) → 剪枝
     - current_sum > target + tolerance（超额太多）→ 剪枝
  3. 从 start 开始遍历剩余金额，依次：
     a. 加入子集
     b. 递归调用
     c. 如果已找到结果则停止
     d. 弹出，尝试下一个
```

### 9.6 `batch_match(invoices, payments, tolerance)`（batch.rs:15-69）

**内部逻辑：**
```
matched = []
unmatched_invoices = []
used_payment_ids = []

对每张发票 invoice（按传入顺序）：
  可用支付 = payments 中未被占用的
  
  if invoice 是 CityTransport 且有行程:
    if 行程条目数 > 1:
      result = match_itinerary_to_payments(invoice, 可用支付, tolerance)
               .or_else(engine.match_one_to_many)
    else:
      result = engine.match_one_to_many(invoice, 可用支付)
  else:
    result = engine.match_one_to_one(invoice, 可用支付)
  
  if result 成功:
    标记使用的支付为已占用
    matched.push(result)
  else:
    unmatched_invoices.push(invoice)

未匹配支付 = payments 中未被占用的

返回 BatchMatchResult { matched, unmatched_invoices, unmatched_payments }
```

### 9.7 `match_itinerary_to_payments(invoice, payments, tolerance)`（batch.rs:73-159）

**内部逻辑（两轮匹配算法）：**

**第 1 轮：宽容匹配（确定真实商户）**
```
provider = invoice.itineraries[0].provider（如 "滴滴"）
对每个行程条目 entry：
  优先找 provider 对应商户的支付（find_best_payment with merchant_filter）
  没找到则不限商户再找一次
  记录找到的支付

统计各商户出现次数 → 取出现最多的为 real_merchant
```

**第 2 轮：精确锁定**
```
清空之前匹配结果
对每个行程条目 entry：
  仅从 real_merchant 的支付中匹配（find_best_payment with real_merchant）
  任何一个条目匹配不上 → 返回 None（整体失败）
```

返回 `MatchResult { match_type: OneToMany, confidence: 1.0 - diff/amount }`

### 9.8 `find_best_payment(entry, payments, used_ids, merchant_filter, tolerance)`（batch.rs:163-218）

**内部逻辑：**
```
对每笔可用支付（未使用、符合 merchant_filter）：
  if pay.amount / entry.amount 不在 0.33~3.0 范围 → 跳过（金额比例异常）
  
  if |pay.amount - entry.amount| <= tolerance:
    精确匹配候选，取差额最小的
  elif pay.amount > entry.amount 且差额 <= entry.amount:
    含高速费候选（支付比行程多，可能含高速费）
    检查 is_same_day_or_next_morning → 时间在同天或次日凌晨才接受

优先返回精确匹配，其次含高速费匹配
```

### 9.9 `is_same_day_or_next_morning(itinerary_time, payment_time)`（batch.rs:221-239）

**内部逻辑：**
1. 从两地字符串中 `extract_date` 提取 YYYY-MM-DD
2. 解析为 `NaiveDate`
3. 计算 `(pay_date - itin_date).num_days()`
4. 差值为 0（同天）或 1（次日凌晨）→ 返回 true
5. 无法解析日期 → 放宽限制返回 true

### 9.10 `extract_date(time_str)`（batch.rs:243-266）

**内部逻辑：**
1. 字符串长度 >=10 且第 5 字节是 '-' → 取前 10 字符（标准 YYYY-MM-DD）
2. 字符串长度 >=5 且第 3 字节是 '-' → 格式化为 "2026-MM-DD"（MM-DD 格式）

4. 均失败 → 空字符串

### 9.11 `MultiDimensionalScorer`（scoring.rs:47-86）

**内部逻辑：**
```
score(invoice, payment):
  amount_score = max(
    score_amount(invoice.amount, payment.total_value()),
    score_amount(invoice.amount, payment.amount)
  )
  merchant_score = score_merchant(invoice.seller_name, payment.merchant_name)
  time_score = score_time(invoice.date, payment.transaction_time)
  category_score = score_category(invoice.category, payment.category)
  
  total = amount_score * 0.4 + merchant_score * 0.3 + time_score * 0.2 + category_score * 0.1
  return MatchScore { total, amount_score, merchant_score, time_score, category_score, breakdown }
```

### 9.12 `score_amount(invoice_amount, payment_amount)`（scoring.rs:88-99）

**内部逻辑：**
```
diff = |invoice_amount - payment_amount|
if diff == 0 → 1.0
elif diff <= 5 → 1.0 - (diff / 5.0) * 0.5  // 线性递减到 0.5
else → 0.0
```

### 9.13 `score_merchant(invoice_seller, payment_merchant)`（scoring.rs:101-123）

**内部逻辑：**
```
if 任一为空 → 0.0
转小写后：
  if 完全相等 → 1.0
  if 包含关系（A.contains(B) 或 B.contains(A)）→ 0.9
  if Levenshtein 相似度 > 0.7 → 返回相似度
  else → keyword_matching_score
```

### 9.14 `levenshtein_distance(s1, s2)`（scoring.rs:176-209）

**内部逻辑（标准 DP 算法）：**
- `chars1: Vec<char>`, `chars2: Vec<char>`
- 构建 (len1+1) × (len2+1) 矩阵
- `matrix[i][j] = min(matrix[i-1][j] + 1, matrix[i][j-1] + 1, matrix[i-1][j-1] + cost)`
- `similarity = 1.0 - distance / max(len1, len2)`

### 9.15 `keyword_matching_score(seller, merchant)`（scoring.rs:211-234）

**内部逻辑：**
```
酒店品牌：如家/汉庭/锦江/7天/华住/希尔顿/万豪/喜来登/香格里拉
  双方同时含相同品牌 → 0.85
网约车品牌：滴滴/高德/T3/曹操/美团/首汽
  双方同时含相同品牌 → 0.85
餐饮品牌：麦当劳/肯德基/星巴克/必胜客/真功夫/永和大王
  双方同时含相同品牌 → 0.85
否则 → 0.0
```

### 9.16 `score_time(invoice_date, payment_time)`（scoring.rs:125-144）

**内部逻辑：**
```
解析 payment_time 为 NaiveDateTime
计算 |invoice_date - payment_date| 的天数差
days_diff == 0 → 1.0
          <= 1 → 0.9
          <= 3 → 0.7
          <= 7 → 0.5
          > 7 → 0.0
无法解析 → 0.5（中性）
```

### 9.17 `score_category(invoice_category, payment_category)`（scoring.rs:146-162）

**内部逻辑：**
```
按 invoice_category 匹配支付分类关键词：
```

#### 分类汇总
- 遍历所有的 MatchResult
- 按 `invoice.category` 分组汇总 `(count, amount)`

#### 城市间交通费
```

  (Train, "车、船票"),
  (Flight, "飞机票"),
  (TicketChange, "订（退、改签）票"),

对每个类别：如果在 category_map 中有记录，创建 TransportDetail { label, count, amount }

```

```

city_transport_count = raw.0（单据张数）
city_transport_actual_amount = raw.1（实际总金额）
city_transport_daily_std = 80.0                          // 每天标准 80 元
city_transport_max = 80.0 × travel_days                  // 总封顶线
city_transport_amount = min(actual, max)                  // 取小的
```

#### 住宿费
```
对每张 Hotel 发票：
  if 有 hotel_detail:
    nights = detail.nights
    actual_amount = inv.amount
  else:
    nights = (travel_days > 1 ? travel_days - 1 : 1)   // 估算
    actual_amount = inv.amount
  
  total_hotel_nights += nights
  total_hotel_actual += actual_amount
  
  standard_amount = nightly_rate_std × nights           // 标准总价
  total_hotel_reimbursable += min(actual_amount, standard_amount)  // 封顶

创建 HotelLevelDetail { level: hotel_level, persons: 1, days: total_hotel_nights, daily_rate: nightly_rate_std, amount: reimbursable, actual_amount }
```

#### 伙食补助
```
meal_subsidy_amount = travel_days × 100.0
创建 MealSubsidyDetail { persons: 1, days: travel_days, daily_rate: 100.0, amount: meal_subsidy_amount }
```

#### total_amount 计算
```
对每个 MatchResult：
  if Hotel → 用封顶后的金额（min(amount, standard × nights)）
  elif CityTransport → 0.0（统一由 city_transport_amount 计入）
  else → inv.amount
invoice_total = 以上求和 + city_transport_amount（封顶后的市内交通）
total_amount = invoice_total + meal_subsidy_amount
```

## 12. 数据去重（dedup）

### 12.1 `deduplicate_invoices(invoices)`（dedup.rs:8-30）

**内部逻辑：**
```
seen = HashSet<String>()
duplicates = Vec<String>()
unique = Vec<Invoice>()

对每张发票：
  if invoice_number 为空:
    key = "{amount}_{date}_{seller_name}"  // 组合键
  else:
    key = invoice_number                 // 按号码去重
  
  if key 不在 seen 中:
    seen.insert(key)
    unique.push(invoice)
  else:
    duplicates.push(invoice_number)       // 记录重复

*invoices = unique
return duplicates
```

## 13. 输出生成

### 13.1 `generate_reimbursement_html_string(form)`（form_html_generator.rs:28-135）

**内部逻辑：**
生成 `<style> + <table>` 的完整 HTML 报销单，包含：
1. `build_transport_rows(form)` 构建城市间交通费 + 住宿费的左右对齐行

3. 行李托运费（预留，固定 0）
4. 凭据报销伙食费（预留，固定 0）
5. 预借款（预留，固定 0）
6. 申报金额行 = total_amount
7. 核准金额行 = 中文大写（如 "捌仟壹佰叁拾贰元柒角捌分"）

### 13.2 `build_transport_rows(form)`（form_html_generator.rs:138-236）

**内部逻辑（左右对齐布局）：**
```
左列 = 城市间交通费明细 × 3 行 + 小计 1 行 = 4 行
右列 = 住宿费分级（战区级以上/军级/师级/其他人员）× 4 行 + 小计 1 行 = 5 行
总行数 = max(4, 5) = 5

对每行 row_idx 0..5：
  if row_idx == 0: 渲染 "城市间交通费" 标签（rowspan=4）
  if row_idx < 3:  渲染交通费明细或空行
  if row_idx == 3: 渲染交通费小计 + 市内交通费
  if row_idx == 0: 渲染 "住宿费" 标签（rowspan=5）
  if row_idx < 4:  渲染住宿费分级明细或空行
  if row_idx == 4: 渲染住宿费小计
```

### 13.3 `amount_to_chinese(amount)`（form_html_generator.rs:239-302）

**内部逻辑：**
```
amount_cents = round(amount × 100)
yuan = amount_cents / 100
jiao = (amount_cents % 100) / 10
fen = amount_cents % 10

if yuan == 0: 处理 <1 元
else: 逐位转换，每 4 位加单位（仟佰拾），每 4 位一组加万/亿
  数字 0 置 need_zero=true，非零时补零
  digits[yuan 的每位] + units[位数] + big_units[万/亿组]

yuan 部分结尾加 "元"
if jiao==0 && fen==0: 加 "整"
else: digits[jiao] + "角" + digits[fen] + "分"
```

示例：
- 0.00 → "零元整"
- 100.00 → "壹佰元整"
- 8132.78 → "捌仟壹佰叁拾贰元柒角捌分"

### 13.5 `generate_comparison_image_pdf(match_results, invoice_dir, output_path, dpi, destination)`（comparison_image_pdf_generator.rs:47-395）

**内部逻辑：**
1. 遍历所有 MatchResult
2. 对每个非虚拟发票：
   - 调用 `image_embedder::render_pdf_page_to_png` 将 PDF 第 0 页转为 PNG
   - 收集支付信息（微信/支付宝单号）
   - 如果超住宿标准，计算超标准提示
3. 对 CityTransport 带行程的：渲染行程单 PDF 页面 + 行程明细表格（序号、金额、支付单号）
4. 将所有收集到的块（发票图片、行程单图片、行程表格）排序
5. 用 `printpdf` 库创建 A4 横向 PDF：
   - 每个块占一页
   - 发票图片按比例缩放居中显示
   - 底部标注支付单号和超标准提示
   - 行程表格用线条绘制表格

### 13.6 `render_pdf_page_to_png(pdf_path, page_index, output_dir, dpi)`（image_embedder.rs:15-41）

**内部逻辑：**
1. 加载 `pdfium.dll`（通过 `get_pdfium_path`）
2. `Pdfium::bind_to_library` 绑定库
3. `load_pdf_from_file` 加载 PDF
4. `page.render_with_config(PdfRenderConfig)` 渲染为位图
5. `render_page_to_png_impl`：
   - 计算缩放 = dpi / 72
   - 目标宽高 = page.width × scale
   - 渲染位图 → RGBA raw bytes
   - 遍历像素，每 4 字节取前 3（RGBA → RGB）
   - `image::RgbImage::from_raw` 创建图片
   - 保存为 `{pdf_stem}_p{page_index}.png`

### 13.7 `render_pdf_all_pages_to_pngs(pdf_path, output_dir, dpi)`（image_embedder.rs:43-73）

**内部逻辑：**
- 加载 PDF，遍历所有页面
- 每页调用 `render_page_to_png_impl`
- 返回所有生成的 PNG 路径列表
